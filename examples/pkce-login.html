PKCE lets a mobile app sign a user in safely without a client secret. The app proves it started the login by revealing a secret only at the very end.

A mobile app cannot keep a client secret: anyone can unpack it. PKCE replaces the fixed secret with a fresh one per login that never passes through the browser.

the pieces

Solid rings must stay secret. Dashed rings may be seen by others.

the flow

  1. The app makes a random code verifier and hashes it into the code challenge.
  2. The app opens the browser at /authorize with the challenge. The verifier stays in the app.
  3. The user signs in on the auth server's page. The server stores the challenge with the login.
  4. The server redirects back to the app with a one-time auth code.
  5. The app calls /token directly with the code and the verifier.
  6. The server hashes the verifier and compares it with the stored challenge.
  7. If they match, the server returns an access token.

the check

The same hash is computed twice, by two different parties, at two different times. Only the party that made the verifier can produce a match.

questions

Why not just use a client secret?
Anything shipped inside an app can be extracted, so it is not a secret. PKCE makes a new secret for every login instead.
Is it a problem that the challenge is visible?
No. SHA-256 cannot be reversed, so seeing the challenge does not reveal the verifier.
Why always S256 and not "plain"?
With "plain" the challenge equals the verifier, so anyone who saw the first request could finish the login.
Does PKCE replace HTTPS or state checks?
No. Keep HTTPS everywhere and keep the state parameter against cross-site request forgery.
